The API accepts two kinds of credential. Both go in the same header.

| | User access token | Product API key |
| --- | --- | --- |
| Prefix | `nhu_` | `nhpk_` |
| Belongs to | A user | A product |
| Reaches | Everything the user can reach, in every organization they belong to | That one product's API routes, and nothing else |
| Permissions | The user's role in each organization | The role you give the key |
| Stops working when | You delete it, or the user's account is deleted | You deactivate it, or its product or organization is deleted |
| Best for | Your own scripts and the `nh` CLI on your machine | CI and other automation |

<Note>
  Product API keys are on the NervesHub main branch but in no tagged release as of NervesHub 2.5.4. An instance running 2.5.4 or earlier only accepts user access tokens.
</Note>

## Send the credential

Put the token or key in the `Authorization` header with the `Bearer` scheme.

```bash
curl -H "Authorization: Bearer $NERVES_HUB_TOKEN" \
  https://manage.nervescloud.com/api/orgs/acme/products/my_app/devices
```

The server also accepts the scheme `token` in place of `Bearer`. The scheme name is not case sensitive.

## User access tokens

A user access token acts as you.

### Create a token

<Tabs>
  <Tab title="Web interface">
    <Steps>
      <Step title="Open your access tokens">
        Open the user menu and select **Access tokens**.
      </Step>

      <Step title="Create the token">
        Click **New token**. Enter a **Note** that says what the token is for, then click **Create access token**.
      </Step>

      <Step title="Copy it">
        Copy the token shown under **New Token**. It is not shown again.
      </Step>
    </Steps>

    The list shows each token's note and when it was last used. Click **Delete** to revoke a token. Anything using it stops working.
  </Tab>

  <Tab title="CLI">
    Sign in through the browser. `nh` saves the resulting token in its settings file and uses it for later commands.

    ```bash
    nh user login
    ```

    Or sign in with your email and password.

    ```bash
    nh user auth
    ```

    See [CLI configuration](/cli/configuration#sign-in) for both.
  </Tab>

  <Tab title="API">
    Exchange an email and password for a token. `note` is optional and labels the token in your token list.

    ```bash
    curl -X POST https://manage.nervescloud.com/api/users/auth \
      -H "Content-Type: application/json" \
      -d '{"email": "jane@example.com", "password": "...", "note": "build server"}'
    ```

    ```json
    {
      "data": {
        "name": "Jane Doe",
        "email": "jane@example.com",
        "token": "nhu_..."
      }
    }
    ```

    This endpoint refuses an account whose email is not confirmed, and an account with [two-factor authentication](/access/two-factor) turned on. Create the token in the web interface or with `nh user login` instead.
  </Tab>
</Tabs>

### Check a token

```bash
curl -H "Authorization: Bearer $NERVES_HUB_TOKEN" \
  https://manage.nervescloud.com/api/users/me
```

```json
{
  "data": {
    "name": "Jane Doe",
    "email": "jane@example.com"
  }
}
```

## Product API keys

A product API key is a credential for automation that has no person's account behind it. It works on one product only, holds a role of its own, and keeps working when the person who created it leaves the organization.

<Note>
  Product API keys are on the NervesHub main branch but in no tagged release as of NervesHub 2.5.4.
</Note>

### Create a key

You need permission to edit the product's settings. The built-in **Manage** and **Admin** roles have it.

<Steps>
  <Step title="Open the product's API keys">
    In the product, open **Product settings** and select the **API keys** tab.
  </Step>

  <Step title="Create the key">
    Click **Create key**. Enter a **Name**, which is shown in the key list and in the [audit log](/access/audit-log). Choose a **Role**, then click **Create key**.
  </Step>

  <Step title="Copy it">
    Copy the key from the dialog, then click **I've copied it**. Only a hash of the key is stored, so it cannot be shown again. If you lose it, deactivate it and create another.
  </Step>
</Steps>

### Choose a role

A key holds one role, which decides what it may do, the same way a member's role does.

- The built-in roles on offer are **View** and **Manage**. **Admin** is not offered, because what it adds is running the organization, which no key can reach.
- A key can hold one of the organization's custom roles instead. See [Roles](/access/roles).
- You can only give a key a role that grants nothing beyond your own role.

Uploading firmware and creating releases both need **Manage**, or a custom role with the **Upload firmware** and **Create, edit and approve releases** permissions.

### What a key can reach

A key works on these routes for its own product:

- Everything under `/api/orgs/{org_name}/products/{product_name}/`, including devices, firmware, [archives](/updates/archives), [deployment groups](/setup/deployments), releases and [support scripts](/management/support-scripts).
- `GET /api/orgs/{org_name}/products/{product_name}` to read the product.
- `/api/devices/{identifier}` and its sub-routes, for devices in the product.
- The [event stream](/outbound/event-stream) socket.

A key cannot reach anything about a user or a whole organization, and it cannot change the product itself. These return `401`:

- `/api/users/me` and `/api/orgs`
- `/api/orgs/{org_name}/users`, `/keys`, `/ca_certificates`, `/webhooks` and `/iroh_endpoints`
- Listing, creating, updating or deleting products

A request that names any other organization or product returns `404`.

A key cannot open a [remote console](/management/remote-console) or shell. The console socket accepts user access tokens only.

### Deactivate a key

In the **API keys** tab, click **Deactivate** on the key's row, then **Deactivate key**.

- API requests with the key are refused at once.
- Any event stream socket opened with the key is disconnected.
- Deactivation cannot be undone. The key stays in the list, marked deactivated.

The **Last used** column shows when a key last authenticated, to the nearest minute. Check it before you deactivate a key.

## Use a credential with the CLI

`nh` sends whatever is in `--token` or `NERVES_HUB_TOKEN` as the bearer token, so both kinds of credential work.

```bash
export NERVES_HUB_TOKEN=nhpk_...
export NERVES_HUB_ORG=acme
export NERVES_HUB_PRODUCT=thermostat
nh firmware list
```

With a product API key, only commands that use the routes listed above work. `nh user whoami`, `nh org`, `nh key`, `nh ca`, `nh webhook` and `nh device console` need a user access token.

See [CI and automation](/outbound/ci-cd) for a complete pipeline setup.

## Failed authentication

| Status | Cause |
| --- | --- |
| `401 Unauthorized` | The credential is missing, malformed, deleted or deactivated. Also returned when the credential is valid but its role lacks the permission the action needs. |
| `403 Forbidden` | The organization requires two-factor authentication and the token's user has not set it up. See [Two-factor authentication](/access/two-factor). |
| `404 Not Found` | The credential cannot see the organization or product in the URL. |

```json
{
  "errors": {
    "detail": "Resource Not Found or Authorization Insufficient"
  }
}
```
