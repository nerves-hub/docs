This quickstart takes a new Nerves project, connects a device to NervesHub with a [shared secret](/auth/shared-secret), and updates it over the air. At the end you have a device in the web UI, a [signing key](/concepts/firmware-signing), an uploaded firmware and a deployment group that delivers it.

<Note>
  Shared secrets suit hobby and R&D projects. For production, use certificates. See [Device certificates](/auth/device-certificates).
</Note>

## Prerequisites

- A working [Nerves installation](https://hexdocs.pm/nerves/installation.html), including `fwup`. The CLI uses `fwup` to sign firmware.
- Hardware to run it on, and an SD card. A Raspberry Pi 4 is a good option, and any of the Nerves [supported targets](https://hexdocs.pm/nerves/supported-targets.html) works well.
- An account on [NervesCloud](https://manage.nervescloud.com) or on a self-hosted NervesHub.
- An instance with shared secret authentication turned on. See [Feature prerequisites](/hosting/feature-prerequisites#shared-secret-authentication).

The examples use NervesCloud: `manage.nervescloud.com` for you and `devices.nervescloud.com` for devices. Use your own hosts if you self-host.

<Steps>
  <Step title="Install the CLI and sign in">
    Install `nh` with Homebrew, or see [CLI installation](/cli/installation) for other methods:

    ```bash
    brew install nerves-hub/tap/nh-cli
    ```

    If you self-host, point the CLI at your instance first:

    ```bash
    nh config set uri https://your.nerveshub.host
    ```

    Sign in. This opens your browser and shows a code to enter there:

    ```bash
    nh user login
    ```

    Save your organization as a default so you can leave out `--org`:

    ```bash
    nh config set org my-org
    ```
  </Step>

  <Step title="Create the project">
    ```bash
    mix nerves.new my_app
    cd my_app
    export MIX_TARGET=rpi0_2   # your target
    ```
  </Step>

  <Step title="Create a product and a shared secret">
    In the web UI:

    1. Open your organization. If it has no products yet, enter `my_app` in the **Create your first product** form and click **Create product**. Otherwise click **New product**, name it `my_app`, and click **Create Product**. The CLI refuses to upload firmware built for a different product name.
    2. Open **Product settings**.
    3. In the **Shared secrets** card, click **Create secret**.
    4. Copy the key. The secret is not displayed: click the copy button next to the key, labelled **Copy secret**, to copy it.

    If the card says shared secret authentication has not been turned on for the platform, the instance does not allow it. Use [device certificates](/auth/device-certificates) instead.
  </Step>

  <Step title="Create a firmware signing key">
    ```bash
    nh key create my_app_key
    ```

    This generates a key pair, saves it under `~/.nh/keys/<org>/`, and registers the public key with your organization. The private key stays on your machine. You are asked for an optional passphrase to encrypt it.

    List your keys to get the public key:

    ```bash
    nh key list
    ```

    Copy the value in the `KEY` column for `my_app_key`. You add it to your firmware in the next step.

    <Warning>
      Back up the private key. Devices only accept firmware signed by a key they trust, so losing it means you cannot sign updates for devices that trust only that key.
    </Warning>
  </Step>

  <Step title="Add and configure NervesHubLink">
    Add the library to the dependencies in `mix.exs`, next to `nerves_pack`:

    ```elixir
    {:nerves_hub_link, "~> 2.14", targets: @all_targets},
    ```

    Configure it in `config/target.exs`:

    ```elixir
    config :nerves_hub_link,
      host: "devices.nervescloud.com",
      fwup_public_keys: ["<public key from nh key list>"],
      shared_secret: [
        product_key: "<product_key>",
        product_secret: "<product_secret>"
      ]
    ```

    `fwup_public_keys` lists the signing keys the device trusts. The device refuses firmware that is not signed by one of them.

    <Tip>
      Keep real secrets out of version control. Read them from the environment for anything beyond a quick test.
    </Tip>
  </Step>

  <Step title="Build and burn">
    ```bash
    mix deps.get
    mix firmware
    mix burn
    ```

    `mix firmware` builds a `.fw` file and `mix burn` writes it to the SD card. Insert the card and power on the device. It boots, joins the network and connects to NervesHub.
  </Step>

  <Step title="Confirm the device connected">
    In the web UI, open the product and go to **Devices**. A device that connects with a product's shared secret is created on its first connection, so it appears in the list without being added first.

    You can also list devices from the CLI. Run it inside the project directory, or pass `--product my_app`:

    ```bash
    nh device list
    ```

    Note the device's identifier. You need it later.
  </Step>

  <Step title="Build, sign and upload an update">
    Make a visible change and raise the version in `mix.exs`, for example to `"0.2.0"`. Then build, sign and upload:

    ```bash
    mix firmware
    nh firmware upload --key my_app_key
    ```

    Inside a Nerves project, `nh` finds the built image under `_build/` and asks you to confirm it. It signs the file with `my_app_key`, uploads it, and prints the firmware's version and UUID. Copy the UUID.

    Add `--password <passphrase>` if you set a passphrase on the key.
  </Step>

  <Step title="Create a deployment group and turn it on">
    A deployment group says which devices get which firmware. Create one for the firmware you uploaded and turn it on:

    ```bash
    nh deployment create my-group --firmware <uuid> --state on
    ```

    This group has no tag or version conditions, so it matches every device in the product that runs the same platform and architecture as the firmware.

    A new group has [delta updates](/management/delta-updates) on. This first update still downloads the full firmware. The firmware you burned was never uploaded to NervesHub, so there is nothing to build a delta from.

    <Note>
      The web UI calls these **deployment groups**. The `nh` CLI and the HTTP API use the name `deployment`. They are the same thing.
    </Note>
  </Step>

  <Step title="Watch the device update">
    NervesHub places a device in a matching deployment group when the device connects. Your device connected before the group existed, so ask it to reconnect:

    ```bash
    nh device reconnect <identifier>
    ```

    The device then:

    1. Receives the update over its WebSocket connection.
    2. Downloads the firmware.
    3. Verifies the signature against `fwup_public_keys` and applies the update with `fwup`.
    4. Reboots into the new firmware and reconnects.

    Check the device in the web UI, or run `nh device show <identifier>`, to see the new firmware version.
  </Step>
</Steps>

## Ship the next update

Once the group exists, one command signs, uploads and points the group at new firmware:

```bash
mix firmware
nh firmware upload --key my_app_key --deploy my-group
```

From this release on, NervesHub holds both firmware files, so it builds a delta from the firmware your device runs and holds the release back until the build ends. If the build fails, the device waits. NervesHub does not send it the full firmware instead.

- The official Nerves systems, such as `nerves_system_rpi4`, declare the delta sources a build needs. With one of those you have nothing to change.
- If your system's `fwup.conf` declares no delta sources, the build fails. Turn delta updates off for the group before you upload:

  ```bash
  nh deployment update my-group --delta-updatable=false
  ```

- Turning delta updates off does not release a release whose delta has already failed. Turn them off, raise the version, and build and upload again. The new release goes out in full.
- If a release does not reach your device, open the group's **Releases** tab and look at the release's **Delta updates** status. See [Releases wait for their deltas](/management/delta-updates#releases-wait-for-their-deltas).

See [CI/CD](/outbound/ci-cd) to do this from a pipeline.
