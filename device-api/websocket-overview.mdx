Each device holds one WebSocket connection to NervesHub and speaks the Phoenix Channels protocol over it. The connection carries firmware updates, [archives](/updates/archives), [scripts](/management/support-scripts), the [remote console](/management/remote-console) and [extension](/extensions/overview) traffic.

<Note>
  `nerves_hub_link` and the other [client libraries](/integrations/overview) implement this protocol for you. Read this page if you are writing your own client or debugging a connection.
</Note>

## Endpoint

Connect to the instance's device host, which is separate from the web host that serves the dashboard and the HTTP API.

```
wss://{device_host}/socket/websocket
```

For NervesCloud:

```
wss://devices.nervescloud.com/socket/websocket
```

The device endpoint serves the same socket at `/device-socket/websocket`.

Your client must verify the server's certificate. For a self-hosted instance, make sure the device trusts the certificate authority that signed the server's certificate. See [Transport](/connection/transport).

## Authentication

A device authenticates when the socket connects, in one of two ways.

| Method | How the device presents it | Pages |
| --- | --- | --- |
| Device certificate | As the TLS client certificate during the handshake | [Device certificates](/auth/device-certificates), [NervesKey](/auth/nerveskey), [TPM](/auth/tpm), [Just-in-time provisioning](/auth/just-in-time-provisioning) |
| Shared secret | As `x-nh-alg`, `x-nh-key`, `x-nh-time` and `x-nh-signature` headers on the WebSocket upgrade request | [Shared secrets](/auth/shared-secret) |

A connection with neither is refused. When a client certificate is present, it is used and the headers are ignored.

## Message format

Every message is a five-element array.

```
[join_ref, ref, topic, event, payload]
```

| Field | Type | Description |
| --- | --- | --- |
| `join_ref` | string or null | Reference of the join this message belongs to |
| `ref` | string or null | Reference of this message, repeated in its reply |
| `topic` | string | `device`, `console`, `extensions` or `phoenix` |
| `event` | string | Event name, such as `update` or `phx_join` |
| `payload` | object | Event payload |

The `vsn` query parameter on the WebSocket URL chooses the encoding.

| `vsn` | Encoding |
| --- | --- |
| `2.0.0` | JSON in text frames |
| `3.0.0` | The same array encoded as Msgpack in binary frames |

See [Transport](/connection/transport) for when to use Msgpack.

## Topics

| Topic | Purpose |
| --- | --- |
| `device` | Firmware updates, archives, scripts, reboot and status. Every device joins this topic. |
| `console` | The remote IEx console and file transfer. Optional. |
| `extensions` | Health, metrics, logging and the other extensions. Optional. See [Extensions protocol](/device-api/extensions). |
| `phoenix` | Heartbeats only. |

## Join the device topic

Send `phx_join` on the `device` topic. The payload describes the device and the firmware it is running.

```json
["1", "1", "device", "phx_join", {
  "device_api_version": "2.4.0",
  "nerves_fw_uuid": "d9f8c63a-1234-5678-abcd-ef0123456789",
  "nerves_fw_product": "my_app",
  "nerves_fw_version": "1.4.0",
  "nerves_fw_architecture": "arm",
  "nerves_fw_platform": "rpi4",
  "fwup_public_keys": "on_connect",
  "meta": {"firmware_validated": true}
}]
```

| Parameter | Description |
| --- | --- |
| `device_api_version` | The protocol version your client implements. See [Device API versions](#device-api-versions). A missing or invalid value is treated as `1.0.0`. |
| `nerves_fw_uuid`, `nerves_fw_product`, `nerves_fw_version`, `nerves_fw_architecture`, `nerves_fw_platform` | The running firmware's metadata. |
| `nerves_fw_author`, `nerves_fw_description`, `nerves_fw_vcs_identifier`, `nerves_fw_misc`, `fwup_version` | Optional firmware metadata. |
| `fwup_public_keys` | Set to `"on_connect"` to be sent the organization's [firmware signing](/concepts/firmware-signing) keys after joining. |
| `archive_public_keys` | Set to `"on_connect"` to be sent the organization's archive signing keys after joining. |
| `currently_downloading_uuid` | The UUID of a firmware the device is downloading right now. Send it when you rejoin mid-update. Without it, NervesHub ends any update it had in progress for the device. |
| `meta.firmware_validated` | `true` or `false`: whether the running firmware has been validated. Left out, the status is recorded as unknown. |
| `meta.firmware_auto_revert_detected` | `true` when the device booted back into its previous firmware after a failed update. |

If the complete metadata is not sent, NervesHub looks up the firmware by `nerves_fw_uuid`. ESP-IDF devices report their own metadata keys. See [ESP-IDF](/updates/esp-idf).

A successful join is answered with a `phx_reply` whose `status` is `ok`.

```json
["1", "1", "device", "phx_reply", {"status": "ok", "response": {}}]
```

A refused join has `status` `error`, and the response is `{"error": "could not connect"}`. Wait, then join again.

### What the server sends after a join

Depending on the join parameters and `device_api_version`, the server then pushes some of these on the `device` topic. Each is described in [Events](/device-api/websocket-events).

| Event | Sent when |
| --- | --- |
| `fwup_public_keys`, `archive_public_keys` | The join asked for them with `"on_connect"`. |
| `archive` | The device's [deployment group](/setup/deployments) has an archive for it. Needs `2.0.0`. |
| `extensions:get` | Always. Needs `2.2.0`. |
| `scripts/run` | The device, its deployment group or its release has [connecting code](/deployments/connecting-code). Needs `2.1.0`. |
| `update_mode` | Always. Needs `2.4.0`. |
| `update` | The deployment group decides to update the device. |

## Join the console topic

Join `console` to offer a remote console. Send the console protocol version your client implements.

```json
["2", "2", "console", "phx_join", {"console_version": "2.1.0"}]
```

See [Console events](/device-api/websocket-events#console-topic).

## Join the extensions topic

Wait for `extensions:get` on the `device` topic, then join `extensions` with one version for each extension you want to serve. See [Extensions protocol](/device-api/extensions).

## Device API versions

`device_api_version` tells the server which messages your client understands. The server uses it to decide what to send unasked: archives, `extensions:get`, scripts and `update_mode` are only sent to a device that declares the version that introduced them.

| Version | Adds |
| --- | --- |
| `1.0.0` | Firmware updates, status updates, reboot |
| `2.0.0` | Identify, archives |
| `2.1.0` | Scripts run outside the console, firmware and archive public keys |
| `2.2.0` | Extensions |
| `2.3.0` | Firmware validation and auto-revert status |
| `2.4.0` | Checking for, requesting and choosing how the device receives firmware updates |

The `console` topic has its own `console_version`.

| Version | Adds |
| --- | --- |
| `1.0.0` | Remote IEx console |
| `2.0.0` | Sending files to and receiving files from a device |
| `2.1.0` | Acknowledging each chunk of a file sent to the device |

`nerves_hub_link` 2.14.0 declares `device_api_version` `2.4.0`.

<Warning>
  A device set to the `device_managed` update mode that joins with a `device_api_version` below `2.4.0` is moved back to `automatic`. See [Device-managed updates](/updates/device-managed-updates).
</Warning>

## Heartbeats

Send a `heartbeat` event on the `phoenix` topic at a regular interval. `nerves_hub_link` sends one every 30 seconds by default.

```json
[null, "5", "phoenix", "heartbeat", {}]
```

The server replies on the same topic.

```json
[null, "5", "phoenix", "phx_reply", {"status": "ok", "response": {}}]
```

The server closes a socket that has sent nothing for 180 seconds.

## Closed channels and reconnecting

| Event from the server | Meaning | What to do |
| --- | --- | --- |
| `phx_error` | The channel stopped unexpectedly. The socket stays open. | Join the topic again, after a delay. |
| `phx_close` | The channel was closed. | `nerves_hub_link` does not rejoin after this. |

When the socket itself closes, reconnect with a backoff so that a fleet does not reconnect all at once. See [Connection lifecycle](/connection/lifecycle) for how `nerves_hub_link` does it.

A device that connects to the web host's `/device-socket` path can be told to reconnect to the device host instead, if the instance is configured to redirect.

## Identify your client

Send a `User-Agent` header on the WebSocket upgrade request so NervesHub can record which client library and version the device runs. See [Connection lifecycle](/connection/lifecycle).
