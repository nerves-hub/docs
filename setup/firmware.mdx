NervesHub stores Nerves firmware as fwup `.fw` files. A `.fw` file is a ZIP archive that holds the firmware's metadata, its data, and an Ed25519 signature. NervesHub checks the signature when you upload, and the device checks it again before it installs. See [Firmware signing](/concepts/firmware-signing) for how the keys fit together.

This page covers fwup firmware, which is what a product accepts by default. For other formats see [RAUC](/updates/rauc), [ESP-IDF](/updates/esp-idf) and [AtomVM](/updates/atomvm).

## Before you start

- A [product](/setup/products) whose name matches your firmware's product name. NervesHub refuses firmware built for a different product.
- The [`nh` CLI](/cli/installation), signed in, with your organization and product set. See [CLI configuration](/cli/configuration).
- `fwup` installed on the machine that uploads. `nh` uses it to sign `.fw` files.

## Build firmware

Build with the standard Nerves workflow:

```bash
export MIX_TARGET=rpi4
mix firmware
```

The `.fw` file is written under `_build/${MIX_TARGET}_${MIX_ENV}/nerves/images/`.

The firmware's version must be a valid SemVer version, such as `1.4.0`. NervesHub 2.5.0 and later reject uploads with any other version.

## Create a signing key

Signing keys belong to your organization, not to one product. Create one if you have none:

```bash
nh key create my_app_key
```

This generates an Ed25519 key pair, uploads the public key to NervesHub, and saves both halves under `~/.nh/keys/<org>/` as `my_app_key.priv` and `my_app_key.pub`. The private key is encrypted at rest. `--password` sets its passphrase. The passphrase is optional, and `nh` prompts for one when it runs interactively.

You can also see and add keys in the web UI under the organization's settings, on the **Signing keys** page.

To register a public key you generated elsewhere, for example with `fwup -g`, use `nh key add <name> --public-key <file>`.

## Upload firmware

```bash
nh firmware upload ./_build/rpi4_dev/nerves/images/my_app.fw --key my_app_key
```

Inside a Nerves project you can leave the path out. `nh` then looks for a single image under `_build/<MIX_TARGET>_<MIX_ENV>/nerves/images/` and asks you to confirm it.

`nh` reads the firmware's metadata, shows it, signs a temporary copy with `fwup`, and uploads that copy. Your original file is not modified. On success it prints the firmware's version and UUID.

The signing key comes from one of:

| Source | Use |
| --- | --- |
| `--key <name>` | A key made with `nh key create`. Add `--password` if it has a passphrase. |
| `--key-file <path>` | An fwup private key file, as `fwup -g` writes. |
| `NERVES_HUB_PRIVATE_KEY` | An unencrypted base64 private key in the environment. Used when neither flag is given. |

If the file is already signed with a key your organization has registered, upload it as is:

```bash
nh firmware upload my_app.fw --skip-signing
```

You can also upload from the web UI. Open the product's **Firmware** page and click **Upload firmware**, or drop the file anywhere on the page. The web UI does not sign, so the file must already be signed.

### What NervesHub checks

NervesHub refuses an upload when:

- Your organization has no signing keys.
- The signature matches none of your organization's keys.
- The firmware's product name is not the product you uploaded to.
- The version is not valid SemVer.
- Firmware with the same UUID is already in the product. The UUID comes from the firmware's contents, so this means the same build was uploaded before.
- The product has **Require unique firmware versions** on and already holds firmware with this version for the same platform and architecture. The upload fails with "has already been taken for this product". Raise the version in `mix.exs` and build again. The setting is on for products created on NervesHub 2.5.0 or later. Change it in **Product settings**, in the **Firmware** card on the **General** tab, or with `nh product update <product> --require-unique-firmware-version=false`.
- The firmware needs a newer `fwup` than the NervesHub server has.

### Deploy in the same command

`--deploy` creates a [release](/deployments/releases) with the new firmware on a deployment group after the upload succeeds. It does not turn the group on. Repeat it to update several groups:

```bash
nh firmware upload my_app.fw --key my_app_key --deploy production
```

If `--deploy` is not given, `nh` uses the `NERVES_HUB_DEPLOYMENT_NAME` environment variable when it is set. If the upload succeeds and a deployment update fails, the firmware stays uploaded and the error says which group failed.

## List, inspect, download, and delete

```bash
nh firmware list
nh firmware show <uuid>
nh firmware download <uuid>
nh firmware delete <uuid>
```

`download` saves the image in the current directory as `<uuid>` with the extension for its format, which is `.fw` for fwup firmware. Pass `--file <path>` to choose the path.

NervesHub refuses to delete firmware that is the current release of a deployment group, or that devices are in the middle of installing. Deleting firmware also deletes the [deltas](/management/delta-updates) built from it.

## Upload from CI

In a pipeline, give `nh` its settings through the environment and pass the firmware path:

```bash
export NERVES_HUB_TOKEN=...               # a product API key or user access token
export NERVES_HUB_ORG=my-org
export NERVES_HUB_PRODUCT=my_app
export NERVES_HUB_PRIVATE_KEY=...         # unencrypted base64 fwup private key
export NERVES_HUB_NON_INTERACTIVE=true    # fail with an error instead of prompting

mix firmware
nh firmware upload _build/rpi4_prod/nerves/images/my_app.fw --deploy production
```

Always pass the path in CI. Without one, `nh` looks for the image itself and asks you to confirm it, which fails without a terminal. Store the token and the private key as protected secrets in your CI system.

`NERVES_HUB_PRIVATE_KEY` needs an unencrypted fwup key, as `fwup -g` writes. A key made with `nh key create` is encrypted and does not work there. See [Sign in CI](/outbound/ci-cd#sign-in-ci).

See [CI/CD](/outbound/ci-cd) for access tokens, product API keys, and the GitHub Action.
