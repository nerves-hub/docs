A deployment group connects firmware to the devices that should run it. It holds matching conditions, which decide the devices that join it, and a sequence of **releases**, each sending one firmware. A device belongs to at most one deployment group.

<Note>
  The web UI calls these **deployment groups**. The REST API and the `nh` CLI use `deployment` and `deployments` in their paths and command names. They are the same object.
</Note>

## Create a group and turn it on

<Steps>
  <Step title="Upload firmware">
    A group is created with its first firmware. Upload one if you have not already. `--key` names the [signing key](/concepts/firmware-signing) to sign it with:

    ```bash
    nh firmware upload ./_build/rpi4_dev/nerves/images/my_app.fw --key my_app_key
    ```

    Without `--key`, `--key-file` or `--skip-signing`, the upload fails. See [Firmware](/setup/firmware).

    The command prints the version and UUID of the uploaded firmware. To find the UUID of firmware that is already uploaded, run:

    ```bash
    nh firmware list
    ```
  </Step>

  <Step title="Create the deployment group">
    ```bash
    nh deployment create "production" \
      --firmware <UUID> \
      --version "~> 1.0" \
      --tag main
    ```

    | Flag                | Description                                                                                                       |
    | ------------------- | ----------------------------------------------------------------------------------------------------------------- |
    | `<name>`            | The group's name, as the argument. Must be unique within the product.                                              |
    | `--firmware`        | UUID of the firmware for the group's first release. Required.                                                      |
    | `--version`         | An Elixir version requirement that a device's current firmware version must meet. Leave it out to match any version. |
    | `--tag`             | A [tag](/setup/devices) condition. Repeat the flag to list several tags.                                                             |
    | `--tag-operator`    | `and` (a device needs every tag, the default) or `or` (a device needs any one of them).                            |
    | `--delta-updatable` | Whether the group uses [delta updates](/management/delta-updates). A new group has them on. Pass `--delta-updatable=false` to create it with them off. |
    | `--notes`           | Notes describing the group, up to 1,000 characters.                                                                |
    | `--state`           | `on` turns the group on once it exists. Without it the group starts off.                                           |

    In the web UI, open **Deployment groups** and select **New deployment group**. The form asks for **Name**, **Delta updates**, **Notes**, **Platform**, **Architecture**, **Firmware**, **Tag(s) distributed to**, **Tag matching** and **Version requirement**.

    A new group is off. No device receives firmware from it until you turn it on.
  </Step>

  <Step title="Turn the group on">
    ```bash
    nh deployment update "production" --state on
    ```

    In the web UI, open the group and select **Resume**. The same button reads **Pause** while the group is on.
  </Step>

  <Step title="Check the group">
    ```bash
    nh deployment list
    nh deployment show "production"
    ```

    `nh deployment list` shows each group's name, state, device count, version condition and firmware UUID. `nh deployment show` adds the release count, tag conditions, tag operator, [archive](/updates/archives), current release number and notes.

    In the web UI the group page has **Overview**, **Releases**, **Stats**, **Activity** and **Settings** tabs. The badge beside the group's name shows its status: **Paused**, **No devices**, **Rolling out**, **Up to date**, **Awaiting approval** or **Stopped**. The last two only appear when the group has a [workflow](/concepts/deployment-workflows).
  </Step>
</Steps>

## Read the group page

### Overview tab

The **Overview** tab shows how the current release is going:

- **Rollout.** How many of the group's devices are on the release's firmware, with a bar and a legend: **On the release**, **Updating**, **Failed**, and **Waiting**. A group with a [workflow](/concepts/deployment-workflows) lists its steps below the bar. A group without one reads "No steps. Every device that matches gets the release the next time it connects."
- **Devices this release didn't reach.** The devices that do not have the release and are not getting it or waiting for their step, each with what happened.
- **Current release.** The release's **Firmware**, **Archive**, **Delta updates** state, and who released it and when.
- **Device matching.** The group's tags and version condition. If devices outside the group match its conditions, or devices in the group no longer match, this section says how many and offers to move them in or remove them. See [Put a device in a group by hand](#put-a-device-in-a-group-by-hand).

When the group is paused, or a workflow step is waiting for approval or has stopped, a notice at the top of the tab says so and carries the buttons to act on it.

### Stats tab

The **Stats** tab shows how the group's releases went. It opens on the current release. A select switches to another release or to all of them. With all releases selected, the tab shows the same four figures across every release and a **Releases** table.

| Section | What it shows | Needs ClickHouse |
| --- | --- | --- |
| **Succeeded**, **Failed attempts**, **Typical update** | The share of updates that succeeded, how many attempts failed, and the median update time | Yes |
| **Downloaded** | How much devices downloaded, and how much delta updates saved | No |
| **Attempts over time** | Update attempts over the release's life | Yes |
| **How long updates took** | Updates grouped by duration | Yes |
| **Downloads** | What the successful updates downloaded, compared with every device taking the full firmware | No |
| **Why updates failed** | Failed attempts grouped by reason | Yes |
| **By the version devices came from** | One row per source version, with a **Download** column that reads **Delta** or **Full** | Yes |

On an instance without ClickHouse, the sections that need it read "This server doesn't keep update outcomes." See [ClickHouse](/hosting/clickhouse).

## How devices join a group

A device that is in no deployment group joins one when it connects. NervesHub looks for groups in the device's product that:

- are turned on,
- do not have **Lock membership** on,
- have a current release whose firmware platform and architecture match the firmware the device is running,
- have tag conditions the device's tags meet, and
- have a version condition the device's firmware version meets.

If several groups match, the device joins the one whose current release has the highest firmware version. If those are equal, it joins the group that shares the most tags with it, and then the oldest group.

### Put a device in a group by hand

The CLI and the API cannot set a device's group. In the web UI you can, with a role that holds the `device:set-deployment-group` permission:

- **One device.** Open the device. In the **Firmware updates** card on the **Details** tab, the **Deployment group** row has a select that lists the groups whose platform and architecture match the device. Choose one and click **Assign**. When the device is in a group, the row shows the group's name and **Remove…** instead.
- **Many devices.** On the product's **Devices** page, select the devices and use the **Deployment group** bulk action. See [Bulk actions](/management/finding-devices#bulk-actions).
- **Every device that matches a group.** When devices outside a group match its conditions, the **Device matching** section of the group's **Overview** tab says how many and offers **Move them in**.

A device you place by hand does not have to meet the group's tag conditions. It is still checked each time it connects. See [When devices leave a group](#when-devices-leave-a-group).

### Tags

Tags are strings you assign to devices, such as `main`, `qa` or `region-us-east`. A group lists zero or more tags and a tag operator:

| Web UI label            | CLI value | A device matches when                 |
| ----------------------- | --------- | ------------------------------------- |
| **Require all** (default) | `and`   | it has every tag the group lists      |
| **Allow any**           | `or`      | it has at least one tag the group lists |

A group with no tags matches devices whatever their tags.

Tags are only compared when a device connects. If you tag a device that is connected and in no group, it joins a matching group the next time it connects. To make that happen now, run `nh device reconnect <identifier>`. A device that is already in a group stays in it whatever tags you give it.

### Version condition

The version condition is an Elixir version requirement, such as `>= 1.0.0`, `~> 1.2` or `< 2.0.0`, checked against the firmware version the device is running. Leave it empty to match any version.

### Platform and architecture

A group records the platform and architecture of the firmware it was created with. The group's **Settings** tab shows them as **Firmware for**. Create one group per platform and architecture.

### When devices leave a group

A device that is already in a group is checked each time it connects. It leaves the group if its firmware no longer meets the group's version condition, platform or architecture. Changing a group's tags does not remove devices that are already in it.

**Lock membership**, on the group's **Settings** tab, stops both: devices only join or leave a locked group when someone moves them. See [Rollout controls](/deployments/rollout-controls#lock-membership).

## Change a group's conditions

```bash
nh deployment update "production" --tag stable --tag eu
nh deployment update "production" --version ">= 2.0.0"
nh deployment update "production" --tag-operator or
```

`--tag` replaces the whole tag list. `--tag ""` or `--version ""` clears the condition. Only the fields you pass are changed.

In the web UI, edit the **Device matching** card on the group's **Settings** tab.

## Ship a new release

To send new firmware to an existing group, create a release:

```bash
nh deployment update "production" --firmware <NEW_UUID>
```

The new release becomes the group's current release. In the web UI, select **New release** on the group page.

Releases can also carry an archive, a description, notes and connecting code, and can be marked required. See [Releases](/deployments/releases).

<Tip>
  A deployment group does not finish. It stays on and keeps sending its current release to devices that join later.
</Tip>

## Upload and release in one command

`nh firmware upload` can create a release in an existing group as soon as the upload succeeds:

```bash
nh firmware upload my_app.fw --deploy "production"
```

Repeat `--deploy` to update several groups. When the flag is not given, `nh` uses the `NERVES_HUB_DEPLOYMENT_NAME` environment variable if it is set.

`--deploy` does not create a group and does not turn one on. If creating the release fails, the firmware stays uploaded and the error names the group that was not updated. See [CI/CD](/outbound/ci-cd).

## Pause a group

```bash
nh deployment update "production" --state off
```

In the web UI, select **Pause** on the group page. A paused group stops sending its release, even to devices that connect, until you resume it. Devices that are already taking the update finish it.

Pausing does not roll back devices that already have the firmware.

## Delete a group

```bash
nh deployment delete "production"
```

`nh` asks you to confirm. Pass `--yes` to skip the prompt. In the web UI, use **Delete group** at the bottom of the **Settings** tab.

Deleting a group deletes its releases. Its devices leave it and join another group they match when they next connect.
