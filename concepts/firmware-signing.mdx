Every fwup firmware file carries an Ed25519 signature made with a private key you hold. The signature is checked twice: by NervesHub when you upload, and by `fwup` on the device before anything is written. A device refuses firmware it cannot verify.

This page covers fwup firmware and [archives](/updates/archives). ESP-IDF and RAUC use different key types, described in [ESP-IDF](/updates/esp-idf) and [RAUC](/updates/rauc).

## Where the signature is checked

| Where | What is checked | Keys used |
| --- | --- | --- |
| NervesHub, at upload | The file is signed by one of your organization's keys. Unsigned files and files signed by an unknown key are refused. | The Ed25519 public keys registered for the organization. |
| The device, at install | `fwup` verifies the signature before it applies the update. | The public keys `nerves_hub_link` holds: from `fwup_public_keys` in your firmware config, or requested from NervesHub. |

Only the private key can sign. Keep it out of source control, and out of the firmware.

## Create and register a key

Signing keys belong to an organization. Every product in the organization shares them.

<Tabs>
  <Tab title="nh key create">
    ```bash
    nh key create my_app_key
    ```

    This generates the key pair, uploads the public key, and saves both halves under `~/.nh/keys/<org>/` as `my_app_key.priv` and `my_app_key.pub`. The private key file is encrypted at rest, with an optional passphrase.
  </Tab>
  <Tab title="fwup -g">
    Generate the pair with `fwup` and register only the public half:

    ```bash
    fwup -g -o my_app_key
    nh key add my_app_key --public-key my_app_key.pub
    ```

    `fwup -g` writes `my_app_key.priv` and `my_app_key.pub`. The private key file is not encrypted. This is the form `--key-file` and the `NERVES_HUB_PRIVATE_KEY` environment variable expect, so it suits CI.
  </Tab>
</Tabs>

You can also add a public key in the web UI, on the organization's **Signing keys** page. Choose the **fwup (Ed25519)** scheme and paste the base64 public key.

`nh key list` prints each Ed25519 public key in full. That value is what goes into `fwup_public_keys`.

## Give devices the public keys

A device needs at least one public key before it accepts an update.

### Put the keys in the firmware

List the base64 public keys in your firmware config:

```elixir
# config/target.exs
config :nerves_hub_link,
  fwup_public_keys: [
    "base64_public_key_1",
    "base64_public_key_2"
  ]
```

The device accepts firmware signed by any key in the list. Entries that are not strings are ignored.

With keys configured this way, the device does not ask NervesHub for keys. Since `nerves_hub_link` 2.14.0 it also ignores any keys NervesHub sends without being asked. Verification then depends only on what you built into the firmware. Changing the list means shipping new firmware, signed by a key the running firmware already trusts.

### Ask NervesHub for the keys

A device with no `fwup_public_keys` asks NervesHub for keys each time it connects. NervesHub replies with all of the organization's Ed25519 public keys. This needs `nerves_hub_link` 2.2.1 or later.

To request keys even when some are configured, set `request_fwup_public_keys`:

```elixir
# config/target.exs
config :nerves_hub_link,
  fwup_public_keys: ["base64_public_key"],
  request_fwup_public_keys: true
```

When NervesHub replies with keys, they replace the configured list in memory. When it replies with none, the device keeps the keys it has.

<Warning>
  Requested keys come from the same server that supplies the firmware. The signature check then tells you the firmware matches a key NervesHub knows, not a key you built into the device. Put the keys in the firmware if you want verification that does not depend on the server.
</Warning>

## Unverifiable firmware is refused

Since `nerves_hub_link` 2.13.0, a device with no usable public key refuses the update. `fwup` only checks a signature when it is given a key, so earlier versions applied the firmware unverified.

The refusal happens before `update_available/1` is called, so your [Client](/updates/applying-updates) is not asked. The device logs:

```
[NervesHubLink:UpdateManager] Refusing firmware update : no public keys are available to verify the firmware signature
```

It also reports the update to NervesHub as failed, with the reason `Refusing unverified firmware : no public keys available`.

<Warning>
  A device that has no `fwup_public_keys` and receives none from NervesHub stops taking updates on 2.13.0 and later. Before you upgrade `nerves_hub_link`, check that every device either has keys configured or belongs to an organization with at least one Ed25519 signing key.
</Warning>

Two related changes tighten how keys from the server are handled:

| Version | Change |
| --- | --- |
| 2.13.0 | An empty key list from NervesHub no longer clears keys configured on the device. |
| 2.14.0 | Keys NervesHub sends are ignored unless the device asked for them when it connected. The device keeps its own keys and logs a warning. |

When a signature does not match any key the device holds, `fwup` fails and the update is reported as failed. See [failed updates](/updates/applying-updates#when-an-update-fails).

## Sign firmware

`nh firmware upload` signs before it uploads:

```bash
nh firmware upload my_app.fw --key my_app_key
```

See [Firmware](/setup/firmware#upload-firmware) for the other ways to supply the key. To upload a file that is already signed, pass `--skip-signing`. NervesHub still verifies the signature.

To sign without uploading, use `fwup` directly:

```bash
fwup --sign -i my_app.fw -o my_app_signed.fw -s my_app_key.priv
```

## Use more than one key

- **Separate development and production.** Sign release builds with a production key held only by your release pipeline. Build production firmware with only the production public key in `fwup_public_keys`. Development-signed firmware then cannot be installed on production devices.
- **Rotate a key.** Ship firmware that lists both the old and the new public key, signed with the old key. Once devices run it, sign later firmware with the new key. Remove the old public key from the list in a later release.

Removing a key from `fwup_public_keys` only affects devices that receive the firmware built without it.

## Archive keys

Archives are verified the same way, with their own key list. See [Archives](/updates/archives#signing-keys) for `archive_public_keys` and `request_archive_public_keys`.
