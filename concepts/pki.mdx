NervesHub uses cryptography for two separate jobs. One proves which device is connecting. The other lets a device check that firmware came from you. They use different keys and work independently.

## Device authentication

A device connects to NervesHub over TLS and verifies the server's certificate. The device then proves its own identity in one of two ways.

| | Certificate | Shared secret |
| --- | --- | --- |
| The device holds | An X.509 certificate and its private key | A key and a secret |
| The device proves itself by | Presenting the certificate in the TLS handshake | Signing its identifier with the secret (HMAC) |
| Identity is per | Device | Device (`nhd_` key) or product (`nhp_` key) |
| Instance prerequisite | None | Shared secrets turned on. See [Feature prerequisites](/hosting/feature-prerequisites#shared-secret-authentication). |
| Page | [Device certificates](/auth/device-certificates) | [Shared secret](/auth/shared-secret) |

### Device certificates and signer certificates

Each device has two pieces of material:

- **A device certificate.** Its common name is the device identifier.
- **A private key.** It stays on the device. It can live on the filesystem, in a [NervesKey](/auth/nerveskey) or in a [TPM](/auth/tpm).

A device certificate is normally signed by a signer certificate, also called a CA certificate. This is a certificate you create and register with your organization. It is not a certificate from a public certificate authority. You register only the certificate. NervesHub never sees the CA private key. To register a CA you prove that you hold its key by signing a verification certificate with it.

Keep the CA private key secret. NervesHub trusts device certificates it signs.

### Certificates are pinned

NervesHub keeps each device's certificates on file and looks up a connecting certificate by its fingerprint. The registered CA only matters the first time a certificate is seen.

1. If the certificate is on file, the device is allowed. Its expiry is not checked.
2. If the certificate is new and self-signed, the device is refused. A self-signed certificate is only accepted when it was uploaded for the device.
3. If the certificate is new but its public key belongs to a known device, the device has renewed its certificate. NervesHub checks that the common name matches the device, that a CA registered in the device's organization signed it, and that the certificate validates. It then records the new certificate.
4. If neither the certificate nor the key is known, NervesHub checks that the certificate has a common name, that a registered CA signed it, and that it validates. It then looks for a device with that identifier in the CA's organization.
5. If the device does not exist, the connection is refused, unless the CA has a [just-in-time provisioning](/auth/just-in-time-provisioning) profile. In that case NervesHub creates the device.
6. If the device already has a certificate on file with a different key, the connection is refused. A device is expected to use one public key.
7. Otherwise NervesHub records the certificate and allows the device.

A deleted device is refused at every step until it is restored.

Because certificates are pinned, removing a CA does not disconnect devices whose certificates are already on file.

### Shared secrets

With a shared secret the device sends its key and a signature over its identifier, made with the secret. The secret is not sent. NervesHub accepts a signature for 90 seconds, so the device clock matters.

A product key is shared by every device in a product. A device holding one can connect as any identifier in that product, so one leaked device exposes the whole product. A device key authenticates one device only. See [Shared secret](/auth/shared-secret).

## Firmware signatures

For fwup firmware, signing is built into `fwup`. Signing keys are Ed25519 key pairs, not certificates, and they are not part of the TLS chain. Other firmware formats use their own key types. See [Firmware signing](/concepts/firmware-signing).

The signature is checked in two places:

1. **On upload.** NervesHub checks the firmware against the signing keys registered with your organization, on its **Signing keys** page.
2. **On the device.** Before applying an update, the device checks the signature against the public keys it holds.

### Where the device gets its public keys

A device takes its public keys from one of two places:

- **Firmware configuration.** Keys listed in `fwup_public_keys` are compiled into the firmware.

  ```elixir
  # config/target.exs
  config :nerves_hub_link,
    fwup_public_keys: ["<base64 public key>"]
  ```

- **NervesHub, when the device connects.** A device with no `fwup_public_keys`, or with `request_fwup_public_keys: true`, asks NervesHub for the organization's keys on connect.

Which you choose decides who the device trusts. With keys compiled in and `nerves_hub_link` 2.14.0 or later, the device rejects firmware that your key did not sign, even if it came from NervesHub. With keys requested on connect, the device trusts whichever server it connected to.

From `nerves_hub_link` 2.13.0, a device refuses firmware and [archives](/updates/archives) it cannot signature-check. A device with no keys configured that receives none from NervesHub stops taking updates until it has some. From 2.14.0, a device ignores keys NervesHub sends unless it asked for them. Earlier versions let keys sent by NervesHub replace the configured ones. The details are in [Firmware signing](/concepts/firmware-signing).
