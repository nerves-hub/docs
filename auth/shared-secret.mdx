title: "Shared secret authentication"
sidebarTitle: "Shared secret"
description: "Connect devices with a key and secret instead of a certificate, using a product key shared by every device or a key issued to one device."
---

With a shared secret, a device authenticates with a key and a secret instead of an X.509 certificate. The device sends the key and signs its identifier with the secret. The secret itself is never sent. It suits development and early R&D.

There are two kinds of key:

| | Product key | Device key |
| --- | --- | --- |
| Prefix | `nhp_` | `nhd_` |
| Belongs to | A product. Every device in it can share one. | One device. |
| Can connect as | Any identifier in the product. | Only that device. |
| Creates the device on first connect | Yes | No. The device exists before the key does. |
| If one device leaks it | The whole product is exposed. | Only that device is exposed. |
| Secret can be read again | Yes, on the product's settings page, by members who can change product settings. | No. It is shown once, when the key is created. |

## Requirements

- Shared secrets must be turned on for the NervesHub instance with `DEVICE_SHARED_SECRETS_ENABLED=true`. It is off by default, and only certificate authentication works without it. See [Feature prerequisites](/hosting/feature-prerequisites#shared-secret-authentication).
- Product keys need NervesHub 2.0.0 or later and `nerves_hub_link` 2.1.0 or later. Shared secret is the default configurator from `nerves_hub_link` 2.4.0.
- Device keys need NervesHub 2.5.0 or later.
- Your firmware must not include the `nerves_key` or `tpm` libraries, or you must set the configurator explicitly. See [Choose the configurator](#choose-the-configurator).

When shared secrets are off, the **Shared secrets** card in **Product settings** says: "Shared secret authentication hasn't been turned on for this platform."

## Use a product key

<Steps>
  <Step title="Create the secret">
    Open **Product settings** in the product sidebar. In the **Shared secrets** card, click **Create secret**. This needs the **Manage** role or higher.
  </Step>

  <Step title="Copy the key and secret">
    The card lists each key. Copy the key, which starts with `nhp_`. Use the copy button next to the key to copy its secret.
  </Step>

  <Step title="Configure the firmware">
    ```elixir
    # config/target.exs
    config :nerves_hub_link,
      host: "devices.nervescloud.com",
      shared_secret: [
        product_key: System.fetch_env!("NERVES_HUB_PRODUCT_KEY"),
        product_secret: System.fetch_env!("NERVES_HUB_PRODUCT_SECRET")
      ]
    ```

    `System.fetch_env!/1` runs when you build the firmware, so the values are compiled into it. Set both variables in the shell or CI job that runs `mix firmware`.
  </Step>

  <Step title="Boot the device">
    The device connects with its serial number as its identifier. If no device with that identifier exists in the product, NervesHub creates one.
  </Step>
</Steps>

## Use a device key

A device key is issued to a device that already exists. A provisioning station typically creates the device and its key together and writes the key and secret to the device.

<Steps>
  <Step title="Issue the key">
    <Tabs>
      <Tab title="New device, web UI">
        Open **Devices**, click **Add device**, and under **How it connects** choose **A shared secret of its own**. After you click **Add device**, the dialog shows the **Key** and **Secret**.
      </Tab>

      <Tab title="Existing device, web UI">
        Open the device's **Settings** tab. In the **Shared secrets** card, click **Create secret**, then **Copy secret**.
      </Tab>

      <Tab title="CLI">
        ```bash
        # Create the device and its key together
        nh device create my-device-001 --shared-secret

        # Or add a key to a device that exists
        nh device shared-secrets create my-device-001
        ```
      </Tab>
    </Tabs>

    <Warning>
      The secret is shown once and cannot be retrieved again. If you lose it, create another key and deactivate the old one.
    </Warning>
  </Step>

  <Step title="Put the key and secret on the device">
    NervesHubLink reads a device key from the `key` and `secret` options:

    ```elixir
    # config/target.exs
    config :nerves_hub_link,
      host: "devices.nervescloud.com",
      shared_secret: [
        key: "nhd_...",
        secret: "..."
      ]
    ```

    Compiling a device key into firmware ties that firmware to one device. To keep one firmware image for the fleet, store the values in the Nerves key-value store instead. NervesHubLink reads `nh_shared_key` and `nh_shared_secret` from it, and they take priority over the config.
  </Step>

  <Step title="Boot the device">
    The device must connect with the identifier of the device the key was issued to.
  </Step>
</Steps>

## Where NervesHubLink looks for the key and secret

NervesHubLink uses the first key it finds, in this order:

1. `nh_shared_key` in the Nerves key-value store
2. `key` in the `shared_secret` config
3. `nh_shared_product_key` in the Nerves key-value store
4. `product_key` in the `shared_secret` config

If the key starts with `nhp_`, the secret comes from `nh_shared_product_secret` in the key-value store, then `product_secret` in the config. For any other key, it comes from `nh_shared_secret` in the key-value store, then `secret` in the config.

## Choose the configurator

`NervesHubLink.Configurator.SharedSecret` is the default only when neither `nerves_key` nor `tpm` is in your project. If one of them is, select shared secrets explicitly:

```elixir
config :nerves_hub_link,
  configurator: NervesHubLink.Configurator.SharedSecret
```

## Check that it works

Open **Devices** in the product. The device shows as **Online** once it connects. For a device key, the **Shared secrets** card on the device's **Settings** tab lists each key with who created it.

If the device does not connect:

- Check the device clock. NervesHub accepts a signature for 90 seconds after it was made. From `nerves_hub_link` 2.13.0, a device whose connection is refused reads the time from the server's response and signs its next attempt with it, so a device that boots with a wrong clock connects on a retry.
- Check that the key is active. A deactivated key shows as **Deactivated** in the card.
- Check that the device has not been deleted. A deleted device's keys stop authenticating, and a product key cannot create a new device under a deleted device's identifier.

## Options

Set these inside `shared_secret`:

<ParamField path="identifier" type="string">
  The identifier the device connects as. Defaults to `Nerves.Runtime.serial_number()`.
</ParamField>

<ParamField path="key_digest" type="atom" default=":sha256">
  The digest used to derive the signing key.
</ParamField>

<ParamField path="key_iterations" type="integer" default="1000">
  The number of PBKDF2 iterations. From NervesHub 2.5.3, a device asking for more than 10,000 is refused.
</ParamField>

<ParamField path="key_length" type="integer" default="32">
  The derived key length in bytes. From NervesHub 2.5.3, a device asking for more than 64 is refused.
</ParamField>

If you write your own configurator for shared secrets, use `nerves_hub_link` 2.13.1 or later. Earlier versions reused a custom configurator's first signature on reconnect, and NervesHub refused it once it expired.

## Deactivate a key

Keys are deactivated, not deleted. A deactivated key stays in the list.

| | Product key | Device key |
| --- | --- | --- |
| Where | **Product settings**, **Shared secrets** card, **Deactivate** | The device's **Settings** tab, **Shared secrets** card, or `nh device shared-secrets delete <identifier> <key>` |
| New connections | Refused | Refused |
| Connections already open | Stay open until the device reconnects | Closed immediately |

Issuing and deactivating device keys are recorded in the device's [audit log](/access/audit-log).

To replace a key, create a new one, move your devices to it, then deactivate the old one.

## Limits

- A device key stays with the device when it moves to another product or organization. Whoever holds the secret can still connect as the device. When a device moves to an organization that should not share credentials with the one it left, issue a new key there and deactivate the old ones.
- A product key lets its holder connect as any identifier in the product, including identifiers that do not exist yet. Use device keys or certificates for production fleets.
